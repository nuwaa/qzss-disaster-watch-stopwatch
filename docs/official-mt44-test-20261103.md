## 10月31日時点の運用判断

11月3日の公式試験までは、現在の `-Capture` ファームウェアで動作を観察します。機能追加やファームウェア変更は原則保留し、試験に支障がある不具合が見つかった場合だけ最小限の修正を検討します。USB-CホストでのGNSS受信、画面表示、受信B・L1S・検証記録件数の増加はユーザーの実機で確認済みです。公式MT44試験情報の実電波受信はまだ確認していません。

現在の記録上限は2ファイル合計約3MBです。5分間の実受信では約53KBの記録が増えましたが、衛星の配信内容や受信条件で増加量は変わります。数日間の連続運用では試験前に満杯になる可能性があるため、「検証記録中」の件数と「検証記録エラー」の有無を適宜確認します。容量到達後は新しい検証ログを保存できません。約3MBの満杯状態からのUSB書き出しは11月1日にユーザー実機で確認しました。

## 公式配信予定

QZSSの[11月配信詳細PDF](https://qzss.go.jp/technical/dod/dc-report/rnhmsi0000003kh5-att/dcx_test_data_details_202611.pdf)では、11月3日（火）13:00～15:00 JSTにMT44の試験情報が予定されています。主な区間は次のとおりです。

| 時刻（JST） | シナリオ |
| --- | --- |
| 13:00～13:30 | Lアラート、楕円パラメータなし |
| 13:30～13:56 | Lアラート、楕円パラメータあり |
| 14:00～14:12 | Jアラート、FDMA |
| 14:15～14:27 | Jアラート、関係省庁 |

区間には意図的な間隔があります。公式案内によると、実際の通報が優先され、試験メッセージが遅延または欠落する場合があります。画面にメッセージが出ない時間だけで受信失敗と判断せず、「L1S受信中」と件数の増加を確認します。

## 記録の範囲と安全性

既存のMT43/44復号・通知判定はそのまま使用します。`-Capture`ビルドでのみ、CRCが正しいMT43/44のSFRBXペイロードを地域で絞らずフラッシュへ記録します。MT44のA1、提供元、災害種別、対象コードの一部、GNSS時刻が安定している場合の受信UTC秒も残します。後でAzarashiを使い、元のSFRBXから全フィールドを再復号します。横浜市外を示す情報も記録します。

内容のあるMT44でA1=0は「訓練・試験」と表示し、自動音・振動を出しません。MT44の空メッセージはA1欄が0でも試験情報として数えません。A1=1/2の実通報候補に対する既存の鮮度・時刻・重複判定は変更しません。A1=3は全解除として扱います。画面の16件履歴とフラッシュの検証記録は別です。フラッシュ記録エラー時も受信・表示・通知処理は続きます。

記録領域は約3.4MBで、この実装は最大約3MB、2ファイルに追記して停止します。古い記録を自動消去しません。録画前の不要な試験ログはPCへ退避・確認後に明示的に消去します。CRCが不正なL1S、NMEA、他衛星のSFRBXは保存しません。

## 11月3日より前の実機確認

以下の作業はStopWatchをPCに接続して行います。COM番号は実機に合わせて変更してください。PowerShellのスクリプト実行制限がある場合は、以前と同様にそのセッションだけ`Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned -Force`を実行します。

1. `& .\scripts\build_capture_export.ps1`と`& .\scripts\upload_capture_export.ps1 -Port COM10`を実行します。書き出し専用画面が出ます。書き込み直後に画面が暗い場合は電源ボタンを短く1回押し、「検証ログ書き出し」を確認します。
2. `python .\scripts\export_watch_capture.py COM10 --initialize`で記録領域を初期化します。既に領域が読める場合には再フォーマットしません。読めない領域は初期化されるので、過去の未抽出記録があり得る場合は先に相談してください。
3. `& .\scripts\build_standalone.ps1 -CaptureTest`と`& .\scripts\upload_standalone.ps1 -Port COM10 -CaptureTest`を実行します。この隔離試験ビルドはUSBホストを開始せず、合成MT44を用います。Aで段階を選び、Bで少なくとも「試験」「発表」「更新」「全解除」を投入します。音・振動は出ないことを確認します。
4. 書き出し専用ファームウェアへ戻し、`python .\scripts\export_watch_capture.py COM10`を実行します。`mt44`と`mt44_a1_test`が0より大きく、`invalid_lines=0`か確認します。保存先はGit管理対象外の`logs/`です。
5. `& .\scripts\build_standalone.ps1 -Capture`と`& .\scripts\upload_standalone.ps1 -Port COM10 -Capture`を実行し、USB-C給電アダプタとGR-M10-C/Sへ接続します。画面の「L1S受信中」、受信B・L1S件数の増加、「検証記録中」の件数増加を確認します。MT43の既知の表示も確認します。
6. 再び書き出し専用ファームウェアにして`python .\scripts\export_watch_capture.py COM10 --clear-after-export`を実行します。**保存先を確かめてから**、空の記録領域を試験当日用に作ります。最後に`-Capture`を再書き込みし、GNSS接続に戻します。

11月3日まではユーザーが連続受信で動作を観察します。約3MBの記録上限に達した場合、受信と表示は続きますが、追加の検証ログは残りません。当日午前に上記の手順でログをPCへ退避し、`--clear-after-export`で空き容量を確保します。

`--clear-after-export`はPC保存・JSON行検証が成功したときだけ端末側の2ファイルを消します。実際の災害情報が含まれる可能性があるため、保存ファイルを公開リポジトリへ追加しないでください。

## 当日の手順

1. 12:30頃までに`-Capture`ビルドで起動し、USB-Cホスト接続のGR-M10-C/Sを衛星が見える場所に置きます。「L1S受信中」、受信B・L1S件数、「検証記録中」を確認します。開始時刻と3つの数値を控えます。
2. 13:00～15:00に、上の区間境界で画面の表示を写真またはメモで記録します。対象地域が端末位置と違ってもログ収集は継続します。A1=0の試験情報では自動音・振動がないことを確認します。真の警報が出た場合、公式情報を確認してください。

4. `python .\scripts\export_watch_capture.py COM10`でJSONLを保存します。`invalid_lines=0`、`mt44>0`、`mt44_a1_test>0`を確認します。`mt44_null`は内容のないMT44で、A1欄が0でも試験情報には数えません。`$env:PYTHONPATH='src;work/deps'; $env:PYTHONUTF8='1'; python .\scripts\decode_watch_capture.py .\logs\watch-capture-YYYYMMDD-HHMMSS-0.jsonl .\logs\watch-capture-YYYYMMDD-HHMMSS-1.jsonl`でAzarashi復号結果を作ります。存在するファイルだけ指定します。
5. 検証後、通常の単体版へ戻す場合は`& .\scripts\build_standalone.ps1`と`& .\scripts\upload_standalone.ps1 -Port COM10`を実行します。端末内ログは意図的に消すまで残ります。

## 合格条件・未対応事項

2026年10月31日時点ではPythonの35テストが成功し、PowerShellスクリプトは構文解析に成功しました。ユーザー実機で両ファームウェアのビルド、合成MT44記録・抽出、5分間の実衛星受信と抽出を確認しました。実衛星分はMT43が130件、MT44空メッセージが119件で、内容のあるMT44試験情報はまだ受信していません。Codex実行環境ではWindowsの`subst`とESP32コンパイラ起動が制限されるため、ビルド・実機操作そのものはユーザー報告に基づきます。11月3日の公式実電波受信は未確認です。

- `-CaptureTest`でMT44のA1=0/1/2/3を記録・抽出・Azarashi再復号できること。合成データは`source=synthetic`で識別できること。
- 衛星の実受信でL1S件数・検証記録件数が増え、既存MT43表示と通知設定が正常であること。
- 試験当日にMT44の実電波受信、A1=0、提供元1/2/3/4、対象地域、L/J/自治体の各シナリオをログで確認できること。**試験前には未検証**です。

- 実災害の通知条件は既存の保守的な時刻・鮮度判定に依存します。国・地域および全対象地域の細かい照合や、すべての公式パターンの実受信検証は今後の課題です。
