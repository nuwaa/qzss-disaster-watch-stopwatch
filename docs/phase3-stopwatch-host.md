# StopWatch v1.0.1自身のUSBホスト化: 接続試験

## 目的と現状

PCを外し、StopWatchのESP32-S3がGR-M10-C/SをUSB機器として認識できるかを検証します。これは最初の**列挙試験**です。試験用ファームウェアは通報を復号・表示しません。元の表示用ファームウェアとは別のPlatformIOプロジェクトにしています。2026-10-31にユーザーの実機で「GNSS CH340 を認識」「1A86:7523」の表示を確認しました。これで列挙段階は成功です。CH340のUART通信やSFRBX受信は、まだこの結果だけでは確認できません。

M5Stackの回路図ではUSB-CのD+/D−がESP32-S3のGPIO20/19につながり、CC1/CC2は5.1kΩのプルダウン、VBUSは5V入力です。ESP32-S3自体はUSB OTGホスト機能を持ちます。ただしUSB Serial/JTAGとOTGは内部PHYを共有するため、列挙試験ではUSB CDC起動を無効にします。これにより実行中のCOMポート表示は使えず、結果は円形画面に出します。配線と給電はUSB-C端子の機器側設計に依存するため、ホストとして実際に動くことはまだ実証していません。

## BSHM2U105C1PBKを使う接続候補

```text
電源 ── USB-C ── BSHM2U105C1PBK の PD入力
StopWatch USB-C ── BSHM2U105C1PBK の Type-C オス
GR-M10-C/S USB-C ── データ対応USB-Cケーブル ── 同製品の Data ポート
```

バッファローの仕様では、PD入力とは別に**データ用ポートが1つ**あり、データ用ポートの供給は最大5V/1.5Aです。この製品自身にUSBホストや復号処理はありません。StopWatchのESP32-S3をホストに切り替えた際、固定プルダウンのUSB-C端子とこのPDパススルーハブの組み合わせでデータ役割が成立するかは公式資料だけでは確定できません。列挙試験で実測します。機器のUSB-C端子以外には配線・給電せず、特に背面BATピンに5Vを加えないでください。

## 列挙試験

1. 現在の表示用ファームウェアの `firmware/stopwatch/.pio/build/m5stack-stopwatch/firmware.bin` が残っていることを確認します。
2. StopWatchを通常どおりPCへUSB-C接続し、`python -m serial.tools.list_ports -v` でStopWatchのCOM番号を確認します。GR-M10-C/SのCH340ポートを指定しないでください。
3. PowerShellで `& .\scripts\build_host_probe.ps1` を実行します。成功した場合だけ `& .\scripts\upload_host_probe.ps1 -Port COM10` を実行します。COM10は確認した番号に置き換えます。
4. PCのUSBからStopWatchを外します。上記の順にBSHM2U105C1PBKと電源、GNSSを接続し、StopWatchを起動します。画面には「USBホスト接続試験」と状態が表示されます。
5. 「USBハブを認識」とVID:PIDが出れば、StopWatchからBSHM2U105C1PBKのUSBデータ経路が見えたことを示します。この旧ホストスタックは外部ハブの先を扱えないため、その段階でGNSSはまだ見えません。「GNSS CH340 を認識」かつ `1A86:7523` ならGNSSのCH340が列挙されたことを示します。実機ではこの表示が確認できました。画面が「USB機器接続待ち」のままなら、給電・CC役割・ハブ互換性を切り分けます。

この試験は現行Arduino-ESP32 2.0.17 / ESP-IDF 4.4のホストAPIで行います。同世代のホストスタックは単一USB機器のみ対応し、外部USBハブの先を扱えません。今回CH340が見えたため、この接続では少なくともCH340までの経路が成立しています。BSHM2U105C1PBKの内部がUSBハブとして列挙されたかは、この表示だけでは断定しません。CH340を読む次の試験にはArduino-ESP32 3.3.9とEspUsbHost 2.10.1を使います。

## CH340からの受信試験

別プロジェクト `firmware/stopwatch-gnss-probe` は、CH340のUARTを9600 bpsに設定し、GNSSの受信byte、NMEA改行、チェックサムが合うUBXフレーム、RXM-SFRBX、QZSS L1Sの件数を画面に表示します。SFRBX出力設定は受信機RAMだけに書き込みます。通報本文の復号・通知は行いません。

2026-10-31の実機確認では、受信byte、UBX、SFRBX、QZSS L1Sの件数がいずれも継続して増加しました。ユーザーが画面で確認した結果であり、具体的な件数や欠落率は記録していません。これでPCを介さないGNSSデータ受信まで確認できました。

1. StopWatchをPCへ接続し、実際のCOM番号を確認します。GR-M10-C/SのCH340の番号を指定しないでください。
2. `& .\scripts\build_gnss_probe.ps1` を実行します。Arduino coreの更新とライブラリのダウンロードにより、初回は時間がかかります。
3. 成功後に `& .\scripts\upload_gnss_probe.ps1 -Port COM10` を実行します。COM10は確認したStopWatchの番号に置き換えます。必要に応じてM5Stack公式手順でダウンロードモードへ入れます。
4. PCから外し、列挙試験と同じBSHM2U105C1PBKの接続へ戻します。画面の「受信 byte」と「UBX / SFRBX」が増えるかを確認します。衛星を捕捉できる場所では「QZSS L1S」も確認します。

表示された数値は受信の診断値です。「NMEA行」は改行数であり、正しいNMEAセンテンス数ではありません。「QZSS L1S」は有効なUBXフレーム内の識別子で数えますが、災危通報の復号成功数ではありません。PCなし通報表示の実装は次の試作版で行います。

## PCなしの通報表示試作

`firmware/stopwatch-standalone` は、既に確認したCH340受信経路からUBX-RXM-SFRBXを読み、L1S CRCを検査してDCR/DCXを表示する試作版です。AzarashiはPython専用のため、マイコン内の本文復号には既存のArduinoライブラリ [QZQSM](https://github.com/baggio63446333/QZQSM) と [QZSSDCX](https://github.com/SWITCHSCIENCE/QZSSDCX) を使います。L1Sの取り出しとCRC判定はAzarashiの実装に合わせ、保存済みの実受信ログで一致を確認しました。Arduinoライブラリの本文がAzarashiと完全に一致するか、実機ではまだ検証していません。

1. StopWatchをPCに接続してStopWatchのCOM番号を確認します。GNSSのCH340を指定しないでください。
2. `& .\scripts\build_standalone.ps1` を実行します。成功時だけ `& .\scripts\upload_standalone.ps1 -Port COM10` を実行し、COM10を実際の番号に置き換えます。
3. PCから外し、前回と同じBSHM2U105C1PBKとGNSSの接続に戻します。画面に「衛星データ受信中」「受信 …B  L1S …」が表示され、CRCを通過したDCR/DCXがあれば本文が表示されます。A/Bボタンで最大8件の履歴を選びます。

画面は大きな文字の概要表示で起動します。A/Bボタンの短押しは履歴送り、A/B同時の短押しは概要表示→従来の文字表示→自動通知の保存記録→概要表示の順に切り替え、同時に約2秒の長押しは手動通知テストです。概要表示では接続状態、通報区分、種別、発表時刻の判定、本文の冒頭を表示します。受信件数と本文の続きは従来の文字表示で確認してください。保存記録画面は未書き込み・未実機確認です。ユーザーが実機で概要画面の本文位置と文字切れがないことを確認しました。

概要表示には図形アイコンと暗い背景色を追加しました。通報待ちは衛星、訓練・試験はフラスコ、古い通報は時計、その他は注意の図形を表示します。通報種別には地震の波形、津波・海上の波、火山、台風などの図形を併記します。背景は受信中の濃紺、訓練・試験の暗い琥珀色、古い通報の暗いグレー、自動通知済みの暗い赤を使います。色だけで判定させず、従来の文字ラベルを残します。2026-10-31、ユーザーが実機で全体の見た目を確認しました。各通報種別や自動通知済み表示を網羅して検証したものではありません。

通報区分7のDCRとメッセージ種別0のDCXは「訓練・試験」と表示します。DCXの空メッセージは履歴に入れません。UBXチェックサム、L1S CRC、対応メッセージ種別を通過したものだけ表示します。同一のL1Sメッセージは履歴内で重複登録しません。通知条件は下の「自動通知の試作条件」を参照してください。実運用・避難判断に使う認証製品ではありません。

受信機から有効なRMCセンテンス（UTC時刻・日付と測位ステータスA）が届いた場合、試作版はDCRの発表時刻との差を画面に表示します。発表から15分超なら「古い通報」、時刻が未取得なら「GNSS時刻未確認」、未来の時刻なら「未来の発表時刻」です。DCXは発表時刻をこの形式で確定できないため「発表時刻未確認」とします。実受信ログに保存されたDCR 73件は、全件が15分超または未来の範囲であり、この新しい時刻判定で新着扱いになりません。2026-10-31、ユーザーがStopWatchの発表時刻表示を実機で確認しました。判定値とAzarashiの発表時刻の一致は未確認です。

StopWatch公式資料では内蔵振動モーターはM5IOE1のPYG9（PYB_MT_PWM）、スピーカーはES8311・AW8737Aを経由します。下記の自動通知実装では、再起動後も同じ通報を通知しないための識別子をNVSに保存します。

M5Unified 0.2.28のStopWatch実装に `M5.Power.setVibration(level)` と `M5.Speaker.tone(...)` があることを確認し、A/Bボタンを同時に約2秒押す手動通知テストを追加しました。画面下に「手動通知テスト」が短く表示され、約250msの振動と短い音を出します。ボタンを離してから再度押すまで繰り返しません。2026-10-31、ユーザーが振動・音・画面表示の3点を実機確認しました。

通知試験用ビルドでは、訓練・古い通報・重複の各条件が無音で、新着DCR模擬だけ音と振動が1回出ることをユーザーが確認しました。スピーカー設定値を64から160へ上げても音はほぼ聞こえないとの報告がありました。M5Stack公式の[StopWatch Speaker例](https://docs.m5stack.com/en/arduino/stopwatch/speaker)は4kHzと10kHzを使用しています。880Hzの音がこの小型スピーカーでは聞き取りにくい可能性があるため、通知音を4kHz・300ms、設定値220に変更しました。ユーザーが実機で聞き取りやすい音になったことを確認しました。

### 自動通知の試作条件

手動テストの成功を受け、DCRの自動通知を追加しました。次の条件をすべて満たす場合だけ、短い振動と音を1回出します。

- UBXチェックサムとL1S CRCが有効で、DCRバージョン1が復号できる
- 通報区分が1～3（訓練・試験の7ではない）、情報形態が0（発表）
- 有効なRMC日時が2回以上連続し、最後の受信から10秒以内
- 発表時刻がGNSSのUTCより未来でなく、発表後3分以内
- UTC時刻が安定してから1分以上経過
- 同じメッセージが画面履歴に未登録で、通知済みIDにも未登録
- 通知済みIDをNVSに保存できる

通知済みIDは64件の循環領域に保存します。保存に失敗した場合は自動通知を停止し、画面に「保存不可・通知無効」と表示します。GNSS時刻待ち、起動後の準備中、通知待機も画面下で区別します。DCXはこの形式で発表時刻を確定できないため、本文表示のみです。履歴表示と手動テストは従来どおり使えます。

準備中の待ち時間が分かるよう、画面下に「通知: 準備中 あとN秒」を表示します。自動通知の条件を満たして振動・音を出した通報は、履歴のバッジを「衛星受信・通知済」とします。訓練・試験や手動通知テストではこのバッジを使いません。ユーザーが修正版の書き込み後、残り秒数が減って「自動通知待機」に変わる動作を実機確認しました。「衛星受信・通知済」は新着DCRの自動通知が未発生のため、まだ実機未確認です。

2026-10-31に保存済みの実受信ログを判定したところ、復号143件中、DCRの通常発表73件はいずれも発表後3分以内ではありませんでした。このログに対する通知候補は0件です。ファームウェアのビルド・書き込みと待機状態は実機確認済みですが、新着通報の自動通知は未検証です。通知機能は研究・実験用であり、防災用の認証済み警報ではありません。

### 自動通知の試験用ビルド

実際の新着通報を待たずに、同じ通知判定関数と保存処理を試せる独立ビルドです。**画面に常時「通知試験モード」「衛星通報ではありません」と表示し、GNSSのUSB受信処理を起動しません。** 通常版の通知済みIDとは別のNVS領域を使います。このビルド中は衛星通報を受信・表示できません。

1. StopWatchをPCに接続し、COM番号を確認します。`& .\scripts\build_standalone.ps1 -NotificationTest` でビルドし、成功後に `& .\scripts\upload_standalone.ps1 -Port COM10 -NotificationTest` で書き込みます。COM番号は実際の値に置き換えます。
2. 画面の番号をA短押しで選び、B短押しで実行します。最初にA+Bを約2秒押し、試験用の通知履歴を消去します。この操作は通常版の通知履歴を消しません。
3. 「1 訓練・試験」と「2 古い通報」では「音・振動なし」を確認します。「3 新着DCR模擬」では1回の音・振動を確認します。同じ画面でBを再度押しても通知されないことを確認します。「4 重複・再起動」でも通知されないことを確認します。
4. StopWatchを再起動すると、保存済みの試験用IDがある場合は「4 重複・再起動」から始まります。Bを押して通知されないことを確認します。
5. 試験後は `& .\scripts\build_standalone.ps1` と `& .\scripts\upload_standalone.ps1 -Port COM10` で通常版に戻します。画面から「通知試験モード」が消え、GNSS受信に戻ったことを確認します。

これは入力条件を人工的に与える試験です。実衛星の新着DCRから自動通知までの一連の動作や、訓練・古い通報を実受信した際の判定を実証するものではありません。結果は各条件の画面表示、音、振動を実機で記録してください。

ユーザーが実機で、訓練・古い通報・重複は無音、新着DCR模擬は1回の音と振動、再起動後の試験用IDは再通知なしと確認しました。その後、通常版を書き込み、GNSS受信画面への復帰を確認しました。これらは試験用NVS領域での結果であり、通常版の実受信における重複抑制は引き続き未確認です。

### 1時間の連続受信と実衛星通報での自動通知

2026-10-31、通常版のPCなし構成で、11:37に海上警報（画面上の発表時刻11:35）が表示されました。「新規通報通知」「衛星受信・通知済」の表示と、音・振動をユーザーが確認しました。11:37、12:07、12:37の受信カウンターはそれぞれ515,226 B、2,267,226 B、3,991,994 B、L1S件数は1,270件、3,552件、5,528件でした。両30分区間で受信カウンターが増加し、12:07と12:37は「衛星データ受信中」「自動通知待機」でした。11:37～12:37に受信停止、再起動、追加の音・振動は報告されていません。11:35発表の海上警報は後の2時点で「古い通報」になりました。

この結果は実機画面とユーザーの観察によるものです。当該フレームの生ログを保存していないため、Azarashiとの独立照合、衛星通報内容の外部確認、通常版NVSでの再起動後の重複抑制は未確認です。再起動試験では、古くなった通報による誤通知がないことと、時刻確認・準備時間を経て通知待機へ復帰することを確認します。この試験だけではNVSによる重複抑制を証明できません。

同日、通常版を起動し直しました。ユーザーの実機では短押しでは起動し直されず、電源ボタンの長押しが必要でした。受信カウンターがリセットされ、その後12,960 B・L1S 13件まで増え、「通知: 準備中 あと50秒」と表示されました。さらに「自動通知待機」へ移行し、受信B・L1S件数が増加し続けることを確認しました。この観察だけではCPUのリセットと電源オフ→オンを区別できません。初回の操作では音・振動の有無を確認できませんでした。

続いてユーザーが通常版を再度起動し、音・振動がなかったことを確認しました。初回の操作で未確認だった音・振動を、この2回目で観察しました。11:35発表の通報はこの時点ですでに古いため、この無音の結果だけでは通常版NVSに保存した通知済みIDの永続的な重複抑制を証明できません。2回目も起動操作の種類は未判別です。

M5Stack公式の[StopWatch操作説明](https://docs.m5stack.com/ja/core/StopWatch)では、電源ボタン短押しは「電源オン／リセット」、2回連続押しは「電源オフ」、PCとのUSB接続時の約2秒長押しは「ダウンロードモード」です。今回の長押し操作はこの区分にそのまま当てはめられないため、過去の記録を電源オフ→オンまたはソフト再起動と断定しません。

次回の起動理由を判断しやすくするため、通常版の画面上部にESP32-S3の[`esp_reset_reason()`](https://docs.espressif.com/projects/esp-idf/en/v5.0/esp32s3/api-reference/system/misc_system_api.html)に基づく「CPU電源投入」「ソフト再起動」「異常後の起動」「起動理由不明」と、起動後の経過分を表示する変更を追加しました。`CPU電源投入`はCPUへの給電開始を示しますが、StopWatch全体の電源オフ操作の履歴を直接証明するものではありません。画面表示に加えて、電源ボタンを押した回数、緑LED、画面の消灯と再点灯も記録します。通常版のビルドは `& .\scripts\build_standalone.ps1`、書き込みは接続ポートを確認して `& .\scripts\upload_standalone.ps1 -Port COM10` を使います。

ユーザーが新しい通常版を書き込み、画面上部に「CPU電源投入 2分」を確認しました。その後、電源ボタンを2回連続で押すと画面と緑LEDが消え、10秒ほど待って短く1回押すと「CPU電源投入 0分」と表示されました。この操作は電源オフ→オンの対照試験として記録できます。一方、電源オン中の短押しは今回の実機では変化がありませんでした。公式の短押しによるリセット記載と異なる観察結果です。今回の結果から、以前の長押し操作の種類を遡って確定することはできません。

給電アダプタとGNSSにつないだ状態で電源ボタンを約2秒長押しすると、画面が消え、緑LEDだけが点灯しました。2回押しによる電源オフ（画面・LEDとも消灯）とは異なる状態です。この状態で短く1回押すと画面が戻り、「CPU電源投入 0分」と表示されました。短押し後にCPUへの給電開始として起動したことは確認できましたが、緑LEDだけの間に通常ファームウェアが動いていたか、ダウンロードモードだったかは未判定です。

### 自動通知の診断記録（通常版は未実機確認）

通常版が実衛星DCRを新規通報として自動通知した時だけ、直近1件のL1S 32バイト、GNSSから算出した受信UTC秒、発表からの秒数、通報区分・発表種別、メッセージIDをNVSの`qzssdiag`領域に保存します。通知済みIDの保存と音・振動の開始を先に行い、診断記録の保存失敗で通知を止めません。保存後に読み返して検査し、失敗時は記録画面に「最新通知の診断保存に失敗」と表示します。A/B同時短押しで概要→文字→記録画面を巡回します。手動通知テスト、訓練・試験、古い通報、DCXでは記録しません。直近1件だけなので、新しい自動通知で上書きされます。

記録画面の4行の16進文字を上から連結し、UTC秒とともにPCで `python scripts/decode_saved_alert.py "<64桁の16進数>" <UTC秒>` を実行すると、AzarashiのJSONと比較できます。このツールは32バイトのL1SからUBX-RXM-SFRBXを再構成します。元の受信機ヘッダーと9番目のワードは保存していないため、元のUBXフレーム全体が一致する証明にはなりません。また、Azarashiによる復号一致だけで、NVSによる再起動後の重複抑制を証明することはできません。

通知試験ビルドでも模擬の32バイトを**別の`qzssdiagt`領域**に保存します。画面には「診断記録あり（試験用）」と表示し、通常版の衛星記録とは混同しません。試験用履歴の消去操作は試験用診断記録も消します。Python側では保存済みの実受信フレーム4種から再構成したL1SのAzarashi復号内容が元のUBXと一致することを確認しました。ユーザーが試験用ビルドを書き込み、「3 新着DCR模擬」で音・振動と「診断記録あり（試験用）」を確認しました。さらに電源ボタン2回でオフにし、短押しで起動した後も同じ記録表示が残ることを確認しました。起動時の音・振動の有無は報告されていません。通常版の診断記録は未確認です。

実機で保存・読出しを確認する時は、通知試験ビルドを書き込み、A+Bを約2秒押して試験履歴を消し、Aで「3 新着DCR模擬」を選んでBで実行します。音・振動と「診断記録あり（試験用）」を確認した後、電源ボタン2回で電源オフ、短押しで電源オンし、同じ表示が残るか確認します。試験後は通常版を書き戻し、GNSS受信に復帰させます。模擬フレームの16進値はAzarashiの実通報復号に使用しません。

## 元の表示用ファームウェアに戻す

PCへStopWatchをUSB-C接続し、M5Stack公式手順に従い電源ボタンを約2秒押して緑LED点灯後に離すとダウンロードモードになります。COM番号を再確認し、`& .\scripts\upload_watch.ps1 -Port COM10` で既存の表示用ファームウェアを書き戻します。必要なら先に `& .\scripts\build_watch.ps1` を実行してください。
