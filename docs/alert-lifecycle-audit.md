# 災危通報の発表・更新・取消：現状調査と最小修正案

2026-10-31 時点。対象は PC を使わない StopWatch USB ホスト版（`firmware/stopwatch-standalone/src/main.cpp`）。研究・実験用であり、防災用の認証済み製品ではない。実機で動作している USB-C の受信経路は維持する。

## 参照した公式資料

- [災危通報アプリケーションノート 第3.0版（2026年10月）](https://qzss.go.jp/technical/dod/dc-report/users-manual.html)：参考資料2の表示・重複判定・有効時間。本文PDFは同ページの免責条項を経由して取得。
- [IS-QZSS-DCR-017（2026年9月）](https://qzss.go.jp/technical/download/ps-is-qzss.html)：緊急地震速報の `It` は `0=発表`、`2=取消`。`1` は現行定義にない。津波警報も同じ `It` を持つ。本文PDFは同ページの免責条項を経由して取得。

アプリケーションノートは、内容が変わった通報を更新として扱う一方、過去のどの通報が更新されたか特定しにくいこと、取消時は表示中の警報を消すこと、同一内容の再受信では通知を繰り返さないことを示す。これはカーナビ向けの表示案であり、端末の全災種に共通する一意のイベントIDを定義するものではない。

## 修正前の判定

| 項目 | 判定 | 根拠と残る問題 |
| --- | --- | --- |
| A1 発表・更新・取消 | **未対応（一部対応）** | `It` 相当の bit 41–42 が `0` の場合だけ自動通知するため、取消自体では通知しない。表示履歴への保存は `It` に依存せず、取消を明示せず、取消前の警報も履歴に残る。異なる内容は別件として表示されるが、更新と断定する仕組みはない。 |
| A2 重複・更新 | **対応済み（一部要確認）** | 32バイトの L1S 全体のIDで8件の画面履歴を重複除外し、自動通知したIDは64件のNVS循環領域に記録する。内容変更は新しい履歴へ反映される。同一イベントの更新に対する再通知方針と、64件から押し出されたIDの再受信は要確認。 |
| A3 受信状態 | **未対応（一部対応）** | USB未接続、CH340/ホスト失敗、15秒以上バイトがない状態は表示する。しかし「衛星データ受信中」はバイト到着で判定し、有効なL1Sの継続受信を意味しない。履歴が空のときは未受信でも「新しい通報はありません」と表示する。 |
| B4 受信履歴 | **一部対応、将来改良** | 直近8件をRAMに表示し、自動通知に使った最後のL1Sと受信UTCをNVS診断記録に保存する。完全な発表・更新・取消履歴、生のUBX連続記録はない。 |
| B5 鮮度・遅延 | **一部対応、将来改良** | 有効なRMC時刻を2回確認し、発表時刻から180秒以内、起動後の60秒準備後に自動通知。未来時刻、15分超の古い情報は通知しない。受信時刻の信頼性、年境界、遅延の独立検証は残る。 |

## 優先度Aの最小修正（実装済み・一部実機確認）

1. `Dc=1`（緊急地震速報）と `Dc=5`（津波警報）の `It=2` を「取消」と表示する。`It!=0` は従来どおり自動通知しない。同じ災種に別内容が来た場合は「発表・別内容」と表示するが、特定の旧報を更新したとは断定しない。
2. 正常分類・発表から300秒以内の取消を受けたら、同じ災種の旧表示を「過去の受信情報」に下げ、取消そのものを最新の表示にする。訓練・試験の旧報と別災種は変更しない。複数同時発表のうちどのイベントが取消されたかは特定できないため、旧報を「取消済」と断定しない。緊急地震速報の旧報は最終受信から5分超でも「過去の受信情報」に下げる。別の発表が引き続き配信されれば、その再受信時に表示を戻すが、重複通知はしない。
3. 受信状態を「GNSS接続待ち」「GNSSデータ未受信」「GNSS受信中・L1S未受信」「L1S受信中」「GNSS受信途絶」「L1S受信途絶」に分けた。CRC正常なL1Sの最終時刻を使い、履歴ゼロ時は「通報未確認／受信状態を確認してください」と表示する。
4. 既存の32バイト重複判定、NVS通知済みID、鮮度判定、USB受信経路は変更していない。

## 実災害を使わない検証

- 専用ライフサイクル試験ビルドはUSBホストとNVS通知保存を起動せず、公開訓練サンプルから生成したCRC正常な合成DCRを投入する。`It=0` 発表、同一フレーム再送、震源の深さを変えた別内容、`It=2` 取消、取消再送、別内容の継続受信の6段階をAで選び、Bで投入する。画面の「試験データ・非衛星」を必ず確認する。この試験は音・振動を発生しない。
- 複数の緊急地震速報を交互に入力し、一件の取消で無関係な発表まで消さないことを確認する。イベントの特定ができない場合はその限界を画面と試験結果に明記する。
- 入力停止、NMEAのみ入力、CRC不正L1S、正常L1S再開を試し、状態表示が「警報なし」を示唆しないことを確認する。
- PC上で合成フレームのCRC・`It`・Azarashi復号を確認した後、診断ビルドを実機に書き込み画面を目視確認し、通常版を戻してUSB-C経路の回帰確認を行う。音・振動の既存通知試験は別ビルドで確認済みであり、この試験では鳴らさない。

試験ビルドのコマンド：

```powershell
& .\scripts\build_standalone.ps1 -LifecycleTest
& .\scripts\upload_standalone.ps1 -LifecycleTest -Port COM10
```

6段階の目視確認後、通常版に戻す：

```powershell
& .\scripts\build_standalone.ps1
& .\scripts\upload_standalone.ps1 -Port COM10
```

試験ビルドでは、B投入後に履歴件数が順に `1→1→2→3→3→3` となる想定。3段目は「試験・別内容」、4段目は「試験・取消」。6段目の継続受信で別内容が再表示されても、通知音と振動は出さない。この試験画面はAが段階選択、Bが投入であり、過去履歴を直接開く操作はない。したがって、旧報の「過去の受信情報」表示そのものは実機で未確認。

### 2026-10-31 の結果

- Codex環境では合成フレームを含むPythonテスト27件が通過。PlatformIOビルドはこの環境の`subst`アクセス拒否とWindows実行制限で完了できなかった。
- ユーザーのPCで専用試験ビルドが `SUCCESS` となり、書き込み後に「試験データ・非衛星」を確認。6段階の試験を「確認完了」と報告した。各段階の写真や生ログは保存していない。
- 通常版をビルド・書き込みし直した後、ユーザーはUSB-C経由で「L1S受信中」と受信B数・L1S件数の増加を確認した。現行のUSB-C受信経路の回帰確認として扱う。
- GNSS側USBだけを抜く試験では、ユーザー提供の切断前写真に「L1S受信中」「受信 149639B  L1S 391」、切断後写真に「GNSS接続待ち」「通知: L1S受信待ち」「受信 156166B  L1S 410」が表示された。ユーザーは再接続後に「L1S受信中」へ戻ったこと、抜き差し中に音・振動がなかったことを報告した。写真のカウンタは取得時刻が違う累積値であり、切断中も受信が続いた証拠とは扱わない。
- 旧報を履歴で開いたときの表示、GNSS接続を保ったままL1Sだけが途絶えた時の表示、実衛星の取消受信は未確認。実衛星の新規通報による自動通知も今回の試験対象外。

優先度Bの完全な履歴保存や生UBX記録は、この修正では実装しない。
